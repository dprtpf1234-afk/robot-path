# 로봇 길찾기 코딩 퍼즐 PRD

2026년 11월 8일 · 허남웅

> 구현 중 PRD와 달라진 점은 맨 아래 「구현 메모」에 적는다 (14절 작업 지침).

## 1. 개요

초등 1~6학년이 SW·AI 행사에서 10~20분 동안 명령 블록을 조립해 로봇을 목적지까지 보내며 순차·반복·조건 개념을 체험하는 터치 기반 웹 게임이다. 혼자 하는 개인 모드(별점·랭킹)와 교사가 운영하는 1:1 실시간 토너먼트(최대 24명, 교사 관전)를 제공하며, GitHub·Vercel·Supabase 무료 요금제만으로 운영한다. 구현은 Claude Code가 이 문서를 기준으로 진행한다.

### 목표

- 1학년도 설명 없이 1분 안에 첫 단계를 시작한다.
- 순차 → 반복 → 조건 순서로 개념을 하나씩 늘려 체험한다.
- 교사 1명이 별도 도구 없이 24명 토너먼트를 진행하고 관전 화면을 전자칠판에 띄운다.
- 매 판 다른 맵과 테마가 나와 반복 플레이해도 새롭게 느낀다.

### 성공 지표 (제안 목표)

| 지표 | 목표 |
|---|---|
| 1장 1단계 완료율 | 90% 이상 |
| 개인 모드 평균 플레이 시간 | 10~20분 |
| 토너먼트 중 연결 문제로 인한 재경기 | 대회당 1회 이하 |
| 랭킹 등록 후 랭킹판 반영 (정상 네트워크) | 15초 이내 |

측정 기준: 「1장 1단계 완료율」 = 1-1을 클리어한 플레이어 세션 수 ÷ 1-1을 시작한 플레이어 세션 수. 「평균 플레이 시간」은 60초 이상 입력이 없는 구간을 뺀 활동 시간이다. 둘 다 stage_events(오프라인 플레이는 대기열로 나중에 전송)로 잰다.

### 용어

- 단계: 맵 하나를 푸는 한 판.
- 레이아웃: 격자 위 길·벽·시작·목적지 배치. 테마와 무관한 구조 데이터.
- 테마: 배경·로봇·목표물·장애물의 겉모습. 레이아웃 위에 입히는 스킨.
- 프로그램: 플레이어가 조립한 블록 목록.

## 2. 사용자

학생은 로그인 없이 닉네임만으로 참여하고, 교사만 로그인해 행사·대회를 운영한다. 학년 폭이 넓어 저학년은 읽기 부담을, 고학년은 지루함을 줄이는 것이 설계의 핵심이다.

| 사용자 | 주요 기기 | 주요 행동 | 설계 고려 사항 |
|---|---|---|---|
| 초등 1~2학년 | 태블릿, 휴대폰 | 1장(순차) 위주로 개인 모드 | 글을 잘 못 읽음 → 아이콘 블록, 크고 짧은 문장, 손가락 애니메이션 튜토리얼 |
| 초등 3~4학년 | 태블릿, 휴대폰 | 1~2장(순차·반복), 랭킹 등록 | 반복 블록을 넣었을 때 블록 수가 줄어드는 것을 보여주기 |
| 초등 5~6학년 | 태블릿, 휴대폰 | 3장(조건)까지, 랭킹 경쟁, 토너먼트 | 챕터를 바로 골라 시작, 별 3개(최소 블록) 도전 |
| 교사·운영진 | 태블릿, 노트북, 전자칠판 | 행사·대회 생성, 대진 관리, 경기 시작, 관전, 랭킹 관리 | 한 화면에서 대회 전체 상황 파악, 큰 버튼 |
| 관객(학부모·대기 학생) | 전자칠판 | 랭킹판·관전 화면 시청 | 멀리서도 보이는 큰 글씨, 조작 없이 자동 갱신 |

기기는 태블릿, 전자칠판, 휴대폰 모두 터치이며, 부스에서는 한 기기를 여러 학생이 돌아가며 쓸 수 있다.

## 3. 핵심 게임플레이

플레이어는 격자 맵을 보고 블록을 조립한 뒤 실행하고, 로봇이 목적지 칸에 들어가는 순간 성공이다. 게임 엔진은 결정론적이어야 한다. 같은 레이아웃과 같은 프로그램은 언제 어디서 실행해도 같은 결과를 내며, 서버 점수 검증과 관전 재생이 모두 이 성질에 기댄다.

### 맵

- 격자 크기 5×5 ~ 8×8.
- 칸 종류: 길, 벽(장애물), 시작, 목적지, 색 타일(빨강·파랑, 3장 조건 블록용).
- 로봇은 한 칸을 차지하고 동·서·남·북 중 한 방향을 바라본다.

### 명령 블록

| 블록 | 표시 | 동작 | 처음 나오는 곳 |
|---|---|---|---|
| 앞으로 | 위 화살표 | 바라보는 방향으로 1칸 이동 | 1장 |
| 왼쪽 돌기 | 왼쪽 회전 화살표 | 제자리에서 90° 왼쪽 회전 | 1장 |
| 오른쪽 돌기 | 오른쪽 회전 화살표 | 제자리에서 90° 오른쪽 회전 | 1장 |
| N번 반복 | 되돌이 화살표 + 숫자 | 안에 넣은 블록을 N번(2~9) 실행 | 2장 |
| 만약 앞이 막혔다면 | 벽 아이콘 + 물음표 | 앞 칸이 벽이거나 맵 밖이면 안의 블록 실행 | 3장 |
| 만약 바닥이 색이라면 | 색 점 + 물음표 | 현재 칸이 지정한 색이면 안의 블록 실행 | 3장 |
| 도착할 때까지 반복 | 깃발 + 되돌이 화살표 | 목적지에 닿을 때까지 안의 블록 반복 | 3장 후반 |

반복·조건 블록은 다른 블록을 담는 그릇 블록이다. 최대 중첩 깊이는 단계와 레이아웃마다 정하며(4절 단계표), 최상위에 놓인 그릇은 깊이 1, 그 안의 그릇은 깊이 2로 센다. 전체 최대 깊이는 2다.

### 엔진 규칙 (구현 기준)

1. 도착: 로봇이 목적지 칸에 들어가는 순간 성공으로 판정하고 실행을 즉시 끝낸다. 남은 명령은 실행하지 않는다. 블록 수는 프로그램에 놓인 전체 블록 수 그대로 센다.
2. 충돌: 벽 칸이나 맵 밖으로 이동하려 하면 둘 다 「충돌」로 같게 처리한다. 로봇은 제자리에 멈추고 실행이 끝난다(실패).
3. 실행 횟수 제한: 블록 실행 1회 = 이동·회전 1번, 조건 검사 1번, 반복의 한 바퀴 시작 1번. 500회까지는 실행하고, 501번째를 시작하려는 순간 「로봇이 지쳤어요」로 끝낸다(실패).
4. 끝까지 실행했는데 목적지가 아니면 실패다.
5. 빈 그릇: 안이 비어 있는 그릇 블록이 있으면 실행 버튼을 누를 때 그 블록을 강조하고 「안에 블록을 넣어 주세요」를 보여주며 실행하지 않는다. 서버도 빈 그릇이 있는 프로그램은 거부한다.
6. 크기 제한: 프로그램은 블록 40개 이하, 중첩은 단계의 최대 깊이 이하, 요청 본문은 16KB 이하. 허용되지 않은 블록이 있으면 서버가 거부한다(팔레트 표시와 별개로 검사).
7. 실행 중 편집: 「실행」을 누른 순간의 프로그램을 스냅샷으로 고정해 실행하고, 애니메이션이 끝날 때까지 편집을 잠근다.
8. 가장 가까이 간 거리(min_distance): 한 시도(7·12절) 안에서 서버가 접수한 모든 실행이 거친 모든 칸(시작 칸 포함)에 대해, 벽을 피해 목적지까지 가는 최단 칸 수(BFS)를 구해 그 최솟값을 쓴다. 한 번도 실행하지 않은 선수는 시작 칸의 거리다.

### 프로그램 조립

- 팔레트의 블록을 탭하면 프로그램 끝에 추가된다(휴대폰 기본 방식).
- 그릇 블록을 선택한 상태에서 탭하면 그 안에 추가된다. 최대 깊이를 넘기는 추가는 막고 이유를 짧게 보여준다.
- 드래그로 순서를 바꾸거나 그릇 안팎으로 옮길 수 있다(보조 방식).
- 반복 횟수 N: 블록의 숫자를 탭하면 − / + 버튼(각 56px)이 나타나 2~9 사이에서 바꾼다. 새 반복 블록의 기본값은 2다.
- 블록의 X 버튼으로 삭제, 「모두 지우기」로 초기화한다. 되돌리기 1단계를 제공한다.

### 실행과 피드백

- 「실행」을 누르면 현재 블록을 강조하며 명령당 0.4초로 로봇이 움직인다. 2배속 버튼을 제공한다. 토너먼트에서는 실행을 누른 순간 서버로 제출되므로 배속은 승패에 영향을 주지 않는다(7절).
- 충돌하면 로봇이 흔들리는 애니메이션과 함께 해당 블록을 빨간 테두리로 표시한다.
- 끝까지 실행했는데 목적지가 아니면 「조금만 더! 다시 해볼까?」를 보여준다. 부정적 표현(틀렸어요 등)은 쓰지 않는다.
- 실패 후에도 프로그램은 그대로 남아 고쳐서 다시 실행한다.
- 힌트(개인 모드 전용): 같은 단계에서 3번 실패하면 힌트 버튼이 나타난다. 누르면 기준 풀이의 최상위 블록 2개(그릇 블록이면 안의 내용 포함)를 보여준다. 풀이는 배정된 변형에 맞게 변환한 것을 쓴다.

### 블록 수와 별점

- 블록 수 = 프로그램에 놓인 모든 블록 개수(그릇 블록 1개 + 그 안의 블록 각 1개). 반복 횟수는 세지 않는다.
- 레이아웃마다 **목표 블록 수(target)**를 데이터에 저장한다. 검증 스크립트가 그보다 짧은 풀이가 없음을 전수 탐색으로 확인한 레이아웃은 화면에 「최적」, 확인하지 못한 레이아웃은 「목표」로 표시한다(5절).
- ★ 1개: 성공 / ★ 2개: 블록 수 ≤ 목표 + 2 / ★ 3개: 블록 수 ≤ 목표.
- 목표보다 적게 푸면(검증 안 된 레이아웃에서만 가능) ★ 3개와 함께 「천재 프로그래머!」 배지를 주고, 서버가 랭킹 등록 때 그 풀이를 stage_results에 남겨 개발자가 목표값을 고칠 수 있게 한다.

## 4. 개인 모드

개인 모드는 3개 챕터 15단계다. 10~20분에 완주한다는 목표는 가정이므로 저학년 테스트로 확인한다. 챕터마다 개념이 하나씩 늘고, 저학년은 1장만 해도 완주한 느낌이 들도록 챕터 완료 화면을 둔다.

### 단계 명세 (서버 검증 기준, content/stages.ts)

| 단계 | 레이아웃 | 허용 블록 | 최대 중첩 | 새 개념 |
|---|---|---|---|---|
| 1-1 | 튜토리얼 T1 (고정) | 앞으로, 돌기 | 0 | 순차 (튜토리얼) |
| 1-2 ~ 1-3 | D1 무작위 | 앞으로, 돌기 | 0 | |
| 1-4 ~ 1-5 | D2 무작위 | 앞으로, 돌기 | 0 | |
| 2-1 | 튜토리얼 T2 (고정) | + N번 반복 | 1 | 반복 (튜토리얼) |
| 2-2 ~ 2-3 | D3 무작위 | + N번 반복 | 1 | |
| 2-4 ~ 2-5 | D4 무작위 | + N번 반복 | 2 | 중첩 반복 |
| 3-1 | 튜토리얼 T3 (고정) | + 만약 앞이 막혔다면 | 2 | 조건 (튜토리얼) |
| 3-2 ~ 3-3 | D5 무작위 | + 만약 바닥이 색이라면 | 2 | 색 조건 |
| 3-4 ~ 3-5 | D6 무작위 | + 도착할 때까지 반복 | 2 | 조건 반복 |

- 허용 블록은 앞 단계의 것을 모두 포함한다(+는 추가되는 블록). 레이아웃은 자기 풀이에 필요한 블록이 단계의 허용 블록에 들어 있고, 자기 maxNesting이 단계 최대 중첩 이하일 때만 후보가 된다.
- 튜토리얼 단계는 손가락 애니메이션이 정해진 블록을 가리켜야 하므로 고정 레이아웃(T1~T3)을 쓰고, 변형도 원본으로 고정한다. 테마만 무작위다. 글은 한 문장을 넘지 않는다.
- 3장 개념 미션: 순차 블록만으로도 풀릴 수 있으므로, 도착 성공과 별개로 「조건 블록을 써서 성공하기」 배지를 둔다. 3장 레이아웃은 순차 블록만 쓰면 목표보다 블록이 크게 늘도록 설계한다.

### 진행 규칙

- 세 챕터는 처음부터 모두 고를 수 있다. 고학년이 바로 2·3장을 시작할 수 있게 하기 위함이다.
- 챕터 안의 단계는 앞 단계를 성공해야 열린다.
- 단계 성공 시 결과 창: 별점, 사용한 블록 수 / 목표 블록 수, 「다음 단계」 「다시 하기」 버튼.
- 챕터 완료 화면: 챕터에서 모은 별 수, 「랭킹에 등록하기」 「다음 챕터」 버튼.

### 기록 저장 (기기 안)

- 단계별 최고 기록은 한 풀이의 묶음으로 저장한다: (레이아웃, 변형, 콘텐츠 버전, 프로그램, 별점, 블록 수, 목표 블록 수). 별점이 높은 기록을 우선하고, 같으면 목표 대비 초과 블록이 적은 기록을 고른다. 서로 다른 풀이의 값을 섞지 않는다.
- 그 밖에 플레이한 (레이아웃, 변형, 테마) 이력과, 아직 서버로 보내지 못한 단계 통계·랭킹 등록 요청(대기열)을 localStorage에 둔다.
- 기기를 돌려 쓰므로 플레이어마다 랜덤 플레이어 세션 id를 발급하고, 기록·대기열의 모든 항목에 붙인다.
- 홈 화면의 「다음 친구에게 넘기기」는 현재 플레이어의 진행·닉네임을 지우고 새 세션 id를 발급한다. 이전 플레이어의 대기 중 요청은 이전 세션 id로 그대로 전송되어 새 학생 기록과 섞이지 않는다. 맵 중복 방지용 플레이 이력은 남긴다.

### 오프라인 동작

- 개인 모드는 /play 한 페이지 안에서 화면을 전환하고(라우트 이동 없음), 서비스 워커가 개인 모드에 필요한 코드·레이아웃·테마를 첫 접속 때 미리 저장한다.
- 보장 범위: 최초 온라인 접속에서 준비를 마친 기기는 네트워크를 끈 뒤에도 모든 단계 이동과 새로고침이 된다. 처음부터 오프라인인 접속은 지원하지 않는다.
- 단계 통계와 랭킹 등록은 대기열에 쌓았다가 연결이 돌아오면 보낸다.

## 5. 맵·테마 시스템

매 판 다른 경험을 주기 위해 레이아웃 × 변형 4종 × 테마 6종을 조합해 무작위로 배정한다. 레이아웃 44개면 약 1,050가지 조합이 나오며, 테마는 겉모습만 바꾸므로 난이도와 목표 블록 수는 변하지 않는다.

### 난이도 등급과 레이아웃 수

| 등급 | 쓰임 | 격자 | 필요한 개념 | maxNesting | 목표 블록 수 | 레이아웃 수 |
|---|---|---|---|---|---|---|
| D1 | 1장 초반, 재경기 최하 | 5×5 | 순차 | 0 | 2~4 | 6 |
| D2 | 1장 후반, 토너먼트 초반 | 6×6 | 순차 | 0 | 5~8 | 10 |
| D3 | 2장 초반 | 6×6 | 반복 | 1 | 3~6 | 6 |
| D4 | 2장 후반, 토너먼트 중반 | 7×7 | 반복(중첩 포함) | 2 | 4~8 | 10 |
| D5 | 3장 초반, 토너먼트 결승 | 7×7 | 조건 | 2 | 4~8 | 6 |
| D6 | 3장 후반, 고학년 결승 | 8×8 | 조건 + 반복 | 2 | 5~9 | 6 |

토너먼트에서 많이 쓰는 D2·D4는 10개씩 만든다(같은 라운드에 거울 반전 맵이 나란히 나오는 것을 줄이기 위함). 총 44개, 그리고 튜토리얼 전용 T1~T3을 따로 둔다.

### 레이아웃 데이터 (저장소의 JSON)

```json
{
  "id": "d3-corner-01",
  "contentVersion": 1,
  "grade": "D3",
  "size": [6, 6],
  "start": { "x": 0, "y": 5, "dir": "E" },
  "goal": { "x": 5, "y": 0 },
  "walls": [[1, 4], [2, 4]],
  "colors": { "red": [], "blue": [] },
  "allowedBlocks": ["forward", "left", "right", "repeat"],
  "maxNesting": 1,
  "target": 5,
  "targetVerified": true,
  "solution": [{ "repeat": 5, "body": ["forward"] }, "left", { "repeat": 5, "body": ["forward"] }]
}
```

좌표는 왼쪽 위가 (0, 0)이고 x는 오른쪽, y는 아래쪽으로 커진다. 북쪽(N)은 y가 줄어드는 방향이다. 위 예시는 동쪽으로 5칸, 왼쪽으로 돌아 북쪽으로 5칸 가는 풀이다. 중첩을 1단계로 제한하면 4블록 이하 풀이가 없어 목표 5가 최적이다(전수 탐색으로 확인). 중첩 2단계를 허용하면 「2번 반복 { 5번 반복 { 앞으로 }, 왼쪽 돌기 }」 4블록으로 풀리므로, maxNesting은 목표값의 일부다.

### 변형 4종 (W×H 격자)

| 변형 | 좌표 변환 | 방향 변환 | 풀이의 돌기 |
|---|---|---|---|
| 원본 | (x, y) | 그대로 | 그대로 |
| 좌우 반전 | (W−1−x, y) | E ↔ W | 왼쪽 ↔ 오른쪽 |
| 상하 반전 | (x, H−1−y) | N ↔ S | 왼쪽 ↔ 오른쪽 |
| 180° 회전 | (W−1−x, H−1−y) | N ↔ S, E ↔ W | 그대로 |

좌표 변환은 start·goal·walls·colors에 모두 적용하고, 방향 변환은 start.dir에 적용한다. 목표 블록 수는 변하지 않는다.

### 레이아웃 검증 (scripts/validate-layouts.ts, 빌드 전 자동 실행)

1. 모든 레이아웃·변형에서 solution이 성공하고, 블록 수가 target과 같으며, allowedBlocks·maxNesting을 지킨다.
2. allowedBlocks·maxNesting 안에서 블록 수 target−1 이하의 모든 프로그램을 전수 탐색해, 성공하는 것이 있으면 빌드를 실패시킨다. 탐색이 제한 시간(레이아웃당 60초)을 넘기면 targetVerified = false로 두고 화면에 「목표」로 표시한다.
3. 튜토리얼을 빼고 id가 중복되지 않고, 등급별 레이아웃 수가 위 표 이상인지 확인한다.

### 테마 6종

| 테마 | 배경 | 로봇 | 목적지 | 장애물 |
|---|---|---|---|---|
| 우주 | 행성 표면 | 탐사 로버 | 에너지 크리스털 | 운석 |
| 바다 | 해저 | 잠수정 | 보물 상자 | 산호초 |
| 마을 | 동네 골목 | 배달 로봇 | 택배 상자 | 공사 펜스 |
| 숲 | 숲속 길 | 탐험 로봇 | 길 잃은 동물 친구 | 나무 |
| 사막 | 모래언덕 | 탐사 로봇 | 오아시스 | 선인장 |
| 눈나라 | 설원 | 썰매 로봇 | 이글루 | 얼음 바위 |

모든 그래픽은 직접 만든 SVG로 하고, 기존 캐릭터나 저작권 있는 이미지는 쓰지 않는다. 테마는 themes.ts에 색상·SVG 컴포넌트로 정의해 추가가 쉽게 한다.

### 배정 규칙 (개인 모드)

1. 현재 단계의 등급·허용 블록·최대 중첩에 맞는 레이아웃을 후보로 모은다.
2. 이 기기에서 아직 플레이하지 않은 레이아웃을 우선하고, 없으면 플레이하지 않은 (레이아웃, 변형) 조합을 고른다.
3. 테마는 직전 단계와 다른 것 중에서 고른다.
4. 남은 후보 중 무작위로 뽑는다. 후보가 없으면 가장 오래전에 플레이한 조합을 고른다.

같은 단계를 「다시 하기」하면 같은 맵을 유지해 별점 개선에 도전할 수 있게 하고, 「다른 맵」 버튼으로만 새로 뽑는다.

### 배정 규칙 (토너먼트)

- 맵은 서버가 고르고, 두 선수는 반드시 같은 레이아웃·변형·테마를 받는다.
- 중복 판단 단위는 (레이아웃, 변형) 조합이다. 같은 대회에서는 미사용 조합을 우선하되, 아직 안 쓴 레이아웃을 먼저 고른다.
- 조합이 소진되면 사용 횟수가 적고 오래전에 쓴 조합을 다시 쓴다.
- 단, 동시에 진행 중인 경기끼리는 같은 레이아웃을 쓰지 않고(옆 경기 보고 따라 하기 방지), 같은 경기의 직전 시도와도 다른 레이아웃을 배정한다. 동시 진행 경기가 그 등급의 레이아웃 수보다 많으면(24명 1라운드 D2 12경기 > 10개) 모자란 만큼만 다른 변형을 허용한다.
- 레이아웃의 solution은 오프라인 힌트를 위해 브라우저에 포함된다. 서버 재검증은 풀이가 유효한지를 보장할 뿐, 학생이 스스로 작성했는지까지는 보장하지 않는다. 토너먼트는 감독이 있는 행사 환경을 전제로 운영한다.

## 6. 랭킹판

랭킹은 교사가 만든 행사 단위로 집계하고, 총 별 수 → 깬 단계 수 → 초과 블록 합 → 등록 시각 순으로 정렬한다. 점수는 서버가 프로그램을 다시 실행해 검증한 뒤에만 저장하고, 공개 화면에는 표시에 필요한 값만 내보낸다.

### 등록 흐름

1. 학생이 챕터 완료 화면이나 홈의 「랭킹 등록」을 누른다.
2. 닉네임을 입력한다. 행사 코드(영문 대문자 5자)는 앱 주소(/?event=ROBOT)나 QR로 미리 설정되고, 없으면 이때 입력받는다.
3. 클라이언트가 POST /api/ranking으로 단계별 최고 기록 묶음(챕터, 단계, 레이아웃 id, 변형, 콘텐츠 버전, 프로그램)과 기기에 쌓인 단계 통계를 보낸다. 요청에는 플레이어 세션 id와 entry key가 들어간다.
4. 서버는 (챕터, 단계)마다 항목이 하나뿐인지, 레이아웃이 그 단계의 후보인지(4절 단계표), 프로그램이 허용 블록·최대 중첩·크기 제한을 지키는지 확인한다. 그다음 같은 엔진으로 재실행해 별점·블록 수를 다시 계산하고, 닉네임을 검사한 뒤 저장한다.
5. 같은 entry key로 다시 등록하면 서버가 단계별로 비교해 더 좋은 묶음만 바꾼다(단계별 결과는 stage_results에 보관). entry key는 128비트 난수로 플레이어 세션마다 발급하고, 서버에는 해시만 저장한다.

### 점수 규칙

- 총 별 수: 단계별 최고 별점의 합(최대 45).
- 동점이면 깬 단계 수가 많은 순.
- 그래도 같으면 초과 블록 합 = Σ max(0, 블록 수 − 목표 블록 수)이 작은 순. 단계마다 맵이 달라 블록 수 자체는 비교할 수 없으므로 목표 대비 초과분만 본다.
- 그래도 같으면 먼저 등록한 순.
- 랭킹판에는 순위, 닉네임, 별 수, 깬 단계 수만 표시한다.
- 레이아웃은 기기가 무작위로 뽑지만 서버는 그 배정을 확인할 수 없다. 행사용 참여형 랭킹으로 보고 이 한계를 받아들인다.

### 닉네임과 안전

- 2~8자, 한글·영문·숫자만. 랭킹에서는 같은 닉네임을 허용한다.
- 비속어 필터: 금칙어 목록(lib/profanity.ts)을 클라이언트와 서버에서 모두 검사한다. 띄어쓰기·특수문자·초성만 쓴 변형도 정규화 후 검사한다.
- 입력 화면에 「진짜 이름은 쓰지 마세요」 안내를 넣는다.
- 교사는 대시보드에서 항목을 숨기거나 삭제할 수 있다.
- 등록 요청은 기기(entry key)당 1분에 5회로 제한한다. 학교 Wi-Fi에서는 모든 기기가 같은 IP로 보이므로 IP 기준 제한은 1분에 100회 정도로 넉넉히 둔다. 제한 카운터는 Supabase 테이블(rate_limits)에 둔다.

### 랭킹 화면

- 공개 조회는 GET /api/ranking/[eventCode]로만 한다. 응답에는 순위, 표시용 번호, 닉네임, 별 수, 깬 단계 수만 들어간다. entry key 해시·내부 id는 내보내지 않는다. 응답은 CDN에 3초까지 캐시한다.
- 학생용: 상위 20명 + 내 순위(내 entry key로 별도 조회).
- 전자칠판용 /ranking/[eventCode]?screen=1: 전체 화면, 큰 글씨, 상위 10명, 새 항목이 들어오면 강조 애니메이션.
- 갱신은 Realtime 연결 대신 5초 간격 조회로 한다. 무료 요금제의 동시 연결 수를 토너먼트에 남겨두기 위함이다.

## 7. 토너먼트 모드

교사가 대회방을 만들고 대진과 경기 시작을 직접 관리하는 단일 탈락전이다. 최대 24명이 1:1 실시간으로 같은 맵을 풀고, 제한시간 안 성공 여부 → 블록 수 → 서버가 접수한 성공 시각 순으로 승자를 정한다. 경기 하나는 여러 시도(처음 + 재경기)로 이루어지며, 시도마다 맵과 시각을 따로 기록한다.

### 진행 흐름

1. 교사가 로그인 후 「대회 만들기」: 대회 이름, 난이도 프리셋, 제한시간(기본 180초, 60~300초)을 정한다. 대회는 행사 하위에 만든다.
2. 숫자 6자리 참가 코드와 QR이 표시된다. 행사 코드(영문 5자)와 형식을 달리해 헷갈리지 않게 한다.
3. 학생은 「대회 참가」에서 코드와 닉네임을 입력하고 대기실에 들어간다. 대회 안에서 닉네임이 겹치면 자동으로 번호를 붙인다(민수, 민수2).
4. 교사 화면에 참가자와 접속 상태가 실시간으로 보인다. 교사는 참가자를 내보낼 수 있고, 25번째 입장은 막는다. 인원 확인과 등록은 서버에서 한 트랜잭션으로 처리한다.
5. 교사가 「참가 마감 · 대진 만들기」를 누르면 1라운드 대진이 무작위로 생성된다. 교사는 두 선수의 자리를 바꾸거나 「다시 섞기」할 수 있다.
6. 교사가 경기를 개별로, 또는 「이 라운드 모두 시작」으로 한꺼번에 시작한다.
7. 시도가 끝나면 서버가 판정한다. 승자가 나오면 교사가 「결과 확정」을 누르고(필요하면 승자 변경), 둘 다 실패하면 재경기 시도가 만들어져 교사가 시작 버튼을 누른다.
8. 라운드의 모든 경기가 확정되면 「다음 라운드 대진 만들기」가 활성화된다. 다음 라운드 대진이 만들어지면 이전 라운드 결과는 바꿀 수 없다.
9. 결승이 끝나면 우승자 발표 화면(전자칠판용)을 띄운다.

교사 운영 화면: 1라운드는 12경기가 동시에 돈다. 그래서 교사의 주 화면은 관전이 아니라 운영형 대진표다. 경기 칸마다 남은 시간, 시도 차수, 선수별 상태(생각 중·성공·제출 완료·접속 끊김)를 보여주고, 거기서 바로 시작·재경기 시작·확정·관전 열기를 한다.

### 대진과 부전승

- 대진은 라운드마다 생존자를 무작위로 짝지어 만든다. 2의 거듭제곱이 아닌 인원(24명 등)도 자연스럽게 처리된다.
- 생존자가 홀수이면 매 라운드마다 1명을 무작위로 부전승 처리한다.
- 이미 부전승을 받은 선수는 후보에서 뺀다. 모두 받은 적이 있으면 직전 라운드 부전승자만 빼고 다시 뽑는다. 생존자가 홀수(3명 이상)일 때만 부전승이 생기므로 후보는 항상 남고, 연속 부전승은 없다.
- 부전승은 대진표에 「부전승」으로 표시하고 자동으로 다음 라운드에 오른다.
- 최소 2명부터 대회를 열 수 있다. 중간에 내보낸 선수는 그 경기에서 기권 처리한다.

### 난이도 프리셋

| 프리셋 | 등급 범위 | 쓰임 |
|---|---|---|
| 저학년 | D1~D3 | 1~3학년 대회 |
| 전체 (기본) | D2~D5 | 학년 섞인 대회 |
| 고학년 | D3~D6 | 4~6학년 대회 |

### 라운드 등급 계산 (매 라운드 대진을 만들 때마다)

1. T = 대회 시작 인원을 올림(인원/2)으로 줄여 1명이 될 때까지의 횟수(시작 때 한 번 계산).
2. k = 지금 생존자 수로 같은 계산을 한 남은 라운드 수(이번 라운드 포함). 기권·내보내기로 생존자가 줄면 k도 줄어든다.
3. k = 1(생존자 2명)이면 결승이며 최고 등급. T = 1인 2명 대회도 같다.
4. 그 외에는 r = T − k + 1, 등급 = 최저 + round((r − 1) × (최고 − 최저) / (T − 1)). 반올림은 0.5를 올리는 방식(JavaScript Math.round)이다.

24명, 「전체」 프리셋 예시

| 라운드 | 시작 인원 | 경기 수 | 부전승 | 등급 |
|---|---|---|---|---|
| 1라운드 | 24 | 12 | 0 | D2 |
| 2라운드 | 12 | 6 | 0 | D3 |
| 3라운드 | 6 | 3 | 0 | D4 |
| 준결승 | 3 | 1 | 1 | D4 |
| 결승 | 2 | 1 | 0 | D5 |

총 23경기다. 9명이면 9 → 5 → 3 → 2 → 1로, 세 라운드에서 부전승이 나온다. 예상 소요 시간(추정): 한 라운드가 카운트다운·제한시간 180초·판정·확정까지 약 4~5분이므로, 24명 대회는 재경기 없이 약 25분이다. 재경기가 나오면 그 라운드가 3~4분씩 늘어난다.

### 경기 규칙

- 두 선수는 같은 맵을 받고 서버 시각 기준 3-2-1 카운트다운 후 동시에 시작한다.
- 「실행」을 누르는 순간 프로그램이 서버로 바로 제출되고, 애니메이션은 화면에서만 재생한다. 배속과 기기 성능은 승패에 영향을 주지 않는다.
- 경과 시간 = 서버 접수 시각 − start_at − 누적 일시정지 시간.
- 마감은 서버 접수 시각 기준 ends_at이며 유예 시간은 없다. 선수 화면은 서버 시각으로 보정한 타이머를 보여주고 ends_at에 실행 버튼을 잠근다. start_at 이전에 도착한 제출도 거부한다.
- 제한시간 안에는 몇 번이든 실행할 수 있다. 성공하면 그 기록(블록 수, 경과 시간)이 저장되고, 더 적은 블록으로 다시 성공하면 갱신된다.
- 성공한 선수는 「제출 완료」를 눌러 기록을 확정할 수 있고, 그 뒤 기록은 바뀌지 않는다. 두 선수가 모두 완료하거나 시간이 끝나면 시도가 종료된다.
- 같은 실행을 다시 보내도 실행 id로 구분해 한 번만 반영한다.
- 선수 화면에는 상대의 블록을 보여주지 않고 「생각 중 / 실행 중 / 성공!」 상태만 보여준다.
- 힌트는 없다. 블록 팔레트와 최대 중첩은 그 맵의 allowedBlocks·maxNesting을 따른다.

### 승패 판정 순서 (시도마다)

1. 한 사람만 성공 → 성공한 사람 승.
2. 둘 다 성공 → 최고 기록의 블록 수가 적은 사람 승.
3. 블록 수도 같음 → 그 기록의 경과 시간이 짧은 사람 승. 경과 시간까지 밀리초 단위로 같으면 교사가 지정한다.
4. 둘 다 실패 → 한 등급 쉬운 다른 맵으로 재경기 시도를 만든다(최하 D1). 자동 재경기는 최대 2번이고, 시작은 교사가 한다.
5. 두 번째 재경기도 둘 다 실패 → 그 시도의 min_distance(3절 엔진 규칙 8)가 짧은 사람 승.
6. 그래도 같음 → 교사가 승자를 지정하거나 재경기 시도를 한 번 더 만든다(자동 횟수와 별개).

교사는 다음 라운드 대진이 만들어지기 전까지 결과를 바꾸거나, 시도를 일시정지·재경기·기권 처리할 수 있다. 모든 교사 조작은 서버 API를 거치며, 상태 변경과 사유 기록(match_logs)을 한 트랜잭션으로 저장한다.

## 8. 교사 관전 모드

교사와 관객은 진행 중인 경기를 골라 두 선수의 블록 조립과 로봇 움직임을 나란히 본다. 엔진이 결정론적이므로 화면 영상을 보내지 않고 프로그램만 주고받아 관전 화면에서 똑같이 재생한다. 선수의 블록 내용은 선수별 관전 채널로만 흐르며, 선수는 자기 채널에 보내기만 할 수 있고 교사·관객은 받기만 한다(12절).

### 관전 화면 구성

- 상단 중앙: 라운드, 남은 시간(큰 글씨), 시도 차수.
- 좌우 분할: 선수별 닉네임, 맵과 로봇, 지금 조립 중인 블록 목록, 실행 횟수, 최고 기록(블록 수·시간).
- 선수가 실행하면 관전 화면에서도 같은 로봇 애니메이션을 재생한다. 관전 화면은 선수의 배속과 상관없이 항상 1배속으로 재생하고, 새 실행이 오면 이전 재생을 멈추고 새로 시작한다.
- 성공 시 해당 쪽에 축하 효과, 시도 종료 시 승자 발표 연출.
- 교사용 버튼(일시정지, 재경기, 승자 지정)은 하단에 작게 둔다.

### 동기화 규칙

- 실행 이벤트에는 실행 id, 프로그램, 프로그램 버전, 서버 접수 시각이 들어간다.
- 중간에 들어오거나 재접속한 관전 화면은 GET /api/tournament/match/snapshot으로 시도 상태, 선수별 최고 기록, 마지막 실행 프로그램과 로봇 최종 위치를 받아 바로 그린다. 편집 중인 블록은 선수가 다음에 블록을 바꿀 때부터 보인다.

### 보기 방식

- 단일 경기: 기본. 전자칠판에 띄우기 좋은 크기.
- 여러 경기 격자: 한 화면에 최대 4경기를 작게 보고, 탭하면 단일 경기로 크게 본다.
- 관객 화면: 교사가 「관객 화면 열기」를 누르면 읽기 전용 링크(/screen/[token])가 만들어진다. 전자칠판에서 교사 로그인 없이 열 수 있고, 교사 버튼은 없다. 교사가 고른 경기를 따라가거나, 경기가 없을 때는 대진표를 보여준다.

### 관객 토큰

- 관객 화면은 익명 로그인 후 서버 API에 토큰을 보내 확인받고, tournament_viewers에 만료 시각과 함께 등록된다. 채널 구독 권한은 이 등록을 기준으로 RLS가 판단한다.
- 토큰은 대회 종료 24시간 후 또는 생성 48시간 후 중 먼저 오는 때 만료된다. 교사는 언제든 회수할 수 있다.
- 회수·만료 시 서버가 관객 화면에 종료 이벤트를 보내 화면을 닫고, 이후 재접속·재구독은 RLS가 거부한다. 기존 연결이 실제로 끊기는지는 0단계에서 실증한다(14절).

### 대진표 화면

- 라운드별 열로 경기를 보여주고, 경기 상태(대기·진행 중·종료)와 승자를 표시한다. 교사용은 여기에 남은 시간·선수 상태·조작 버튼을 더한 운영형이다(7절).
- 라운드마다 대진을 다시 추첨하므로, 아직 만들지 않은 다음 라운드는 「생존자 N명」으로 표시한다.

### 게임 화면 배치

- 가로 화면(태블릿·전자칠판): 왼쪽 60% 맵, 오른쪽 40% 프로그램과 팔레트.
- 세로 화면(휴대폰): 위 맵, 가운데 프로그램(가로 스크롤), 아래 고정 팔레트, 오른쪽 아래 실행 버튼.
- 맵은 SVG로 그려 화면 크기에 맞게 확대·축소한다.

### 터치 규칙

- 터치 대상은 최소 48×48px, 블록과 주요 버튼은 56px 이상.
- 탭이 기본, 드래그는 보조. 길게 누르기에 기능을 숨기지 않는다.
- 더블탭 확대·당겨서 새로고침을 막고(touch-action, overscroll-behavior), 화면 회전에 대응한다.

### 저학년 배려

- 블록은 아이콘이 주인공이고 글자는 보조(2~5자).
- 본문 18px 이상, 안내 문장은 한 줄.
- 색만으로 정보를 전달하지 않는다(색 타일에 무늬 또는 기호를 함께 표시).
- 효과음은 켜고 끌 수 있게 하고, 동작 없이 60초가 지나면 다음에 눌러야 할 곳을 살짝 빛나게 한다.

## 10. 기술 스택과 아키텍처

Next.js 앱 하나를 Vercel에 배포하고, Supabase가 DB·교사 인증·실시간 통신을 맡는다. 게임 엔진은 화면과 분리된 순수 TypeScript 모듈로 만들어 브라우저와 서버가 같은 코드를 쓴다.

학생·교사 기기는 Vercel의 화면과 API를 거치고, 대결·관전 동기화만 Supabase Realtime에 직접 연결한다. 점수와 승패는 API가 같은 엔진으로 다시 계산해 Postgres에 저장한다.

| 영역 | 선택 | 이유 |
|---|---|---|
| 프레임워크 | Next.js (App Router) + TypeScript | 화면과 서버 API(Route Handler)를 한 프로젝트에서, Vercel 기본 지원 |
| 스타일 | Tailwind CSS | 반응형·터치 크기 조절이 빠름 |
| 맵 렌더링 | SVG + CSS transition | 어떤 화면 크기에서도 선명, 별도 게임 엔진 불필요 |
| 드래그 | dnd-kit | 터치 드래그 지원 |
| 클라이언트 상태 | Zustand | 게임 화면 상태를 간단히 관리 |
| DB·인증·실시간 | Supabase (Postgres, Auth, Realtime Broadcast·Presence) | 무료 요금제로 행사 규모 충분 |
| 학생 식별 | Supabase 익명 로그인 | 가입 없이 대회에서 자기 기록만 쓰도록 RLS 적용 |
| 배포 | Vercel Hobby + GitHub 연동 | main 푸시 시 자동 배포, PR마다 미리보기 주소 |
| 테스트 | Vitest(엔진·대진 로직), Playwright(주요 흐름) | 결정론적 엔진을 테스트로 고정 |
| QR | qrcode | 참가 코드·행사 주소 QR |

### 폴더 구조

```
src/
  app/                 # 화면과 API (Route Handler)
    play/              # 개인 모드 단일 페이지 (오프라인 대상)
    api/ranking/       # 랭킹 등록(재실행 검증)·공개 조회
    api/stats/         # 단계 통계 수집
    api/tournament/    # 대회·참가·대진·시도 시작·run·done·judge·교사 조작·snapshot
    api/time/          # 서버 시각 (타이머 보정)
  engine/              # 순수 TS: 맵 타입, 실행기, 별점, 거리(BFS), 변형, 프로그램 검사
  tournament/          # 순수 TS: 대진·부전승·등급·승패 판정·맵 배정
  content/layouts/     # 레이아웃 JSON (T1~T3 포함)
  content/stages.ts    # 15단계 명세
  content/themes.ts    # 테마 정의와 SVG
  components/
  lib/supabase/        # 브라우저·서버 클라이언트
  lib/auth.ts          # 교사·선수·관객 권한 확인
  lib/profanity.ts
  sw.ts                # 서비스 워커 (Serwist)
supabase/migrations/   # 테이블·RLS·잠금 함수 SQL
scripts/validate-layouts.ts   # package.json prebuild에서 실행
```

### 원칙

- engine/과 tournament/은 React·Supabase를 import하지 않는다. 그래야 서버에서 그대로 재실행하고 테스트할 수 있다.
- 점수와 승패는 항상 서버가 엔진으로 다시 계산해 저장한다. 클라이언트가 보낸 점수 숫자는 믿지 않는다.
- 모든 서버 API는 요청마다 확인한다: 호출자가 그 대회의 교사인지 또는 그 시도의 선수인지, 요청의 시도 id가 현재 시도인지(이전 시도의 늦은 요청 거부), 시도 상태가 그 동작을 허용하는지.
- 교사 권한은 teachers 테이블에 운영자가 넣은 사용자 ID로만 판단한다. 익명 사용자도 Supabase에서는 authenticated 역할이므로, 로그인 여부나 역할만으로 권한을 주지 않는다.
- 시도 상태를 바꾸는 모든 동작(run 기록, done, judge, 일시정지, 승자 변경)은 시도 행을 잠근(SELECT … FOR UPDATE) Postgres 함수 하나로 처리해 동시 요청에도 결과가 하나로 정해지게 한다.
- 개인 모드 오프라인: Serwist(서비스 워커)로 /play 페이지와 그 코드·레이아웃·테마를 미리 저장한다. 교사·대회·API 응답은 캐시하지 않는다.
- 배포 차단: Vercel은 GitHub Actions 결과를 보지 않고 빌드하므로, 레이아웃 검증과 엔진·대진 단위 테스트를 package.json의 prebuild에 넣어 Vercel 빌드 자체가 실패하게 한다. main은 보호 브랜치로 두고 필수 체크를 통과한 PR만 합친다.
- Supabase service role 키는 서버 환경 변수에만 둔다.
- 환경 변수: NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY, ENTRY_KEY_PEPPER(entry key 해시용).

## 11. 데이터 모델

레이아웃·테마·단계 명세는 저장소의 정적 파일로 두고, Supabase에는 행사·랭킹·통계·대회 기록만 저장한다. 모든 테이블에 RLS를 켜고, **쓰기는 모두 서버 API(service role)**로만 한다. 경기는 대진(matches)과 시도(match_attempts)를 나눠 재경기 기록을 잃지 않는다.

| 테이블 | 주요 컬럼 | 설명 |
|---|---|---|
| teachers | user_id, display_name, created_at | 교사 권한의 유일한 근거. 운영자가 SQL로 추가 |
| events | id, teacher_id, name, code(영문 5자), created_at | 행사. 랭킹·대회의 상위 단위 |
| ranking_entries | id, event_id, entry_key_hash, nickname, total_stars, stages_cleared, excess_blocks, stage_results(jsonb), hidden, created_at, updated_at | 랭킹 항목. 단계별 기록 묶음을 stage_results에 보관 |
| stage_events | id, event_id, player_session, client_event_id(유일), type(start·clear·quit), chapter, stage, grade, active_ms, created_at | 성공 지표용 익명 통계. client_event_id로 중복 전송 제거 |
| tournaments | id, event_id, teacher_id, name, join_code(숫자 6자리), preset, time_limit_sec, status(lobby·running·finished), current_round, planned_rounds, created_at | 대회 |
| tournament_players | id, tournament_id, user_id(익명 인증), nickname, display_name(번호 포함), had_bye, last_bye_round, eliminated_round, kicked, joined_at | 참가자. 대회당 최대 24명 |
| matches | id, tournament_id, round, slot, player_a, player_b(null이면 부전승), current_attempt_id, auto_rematches, winner_id, result_reason, confirmed, locked | 대진 관계와 최종 결과. locked = 다음 라운드 생성 후 변경 불가 |
| match_attempts | id, match_id, attempt_no, layout_id, variant, theme_id, grade, content_version, status, start_at, ends_at, paused_at, paused_ms, result, judged_at | 시도(처음·재경기)마다 맵·시각·판정을 따로 보관 |
| match_records | id, attempt_id, player_id, solved, best_blocks, best_elapsed_ms, min_distance, best_program(jsonb), runs, done, updated_at | 시도·선수별 최고 기록. (attempt_id, player_id) 유일 |
| match_runs | id, attempt_id, player_id, run_id(유일), program, received_at, solved, blocks, min_distance | 실행 하나하나. 재전송 멱등 처리·관전 스냅샷·감사용 |
| match_logs | id, match_id, attempt_id, actor, action, reason, created_at | 교사 조작 기록. 조작과 같은 트랜잭션으로 저장 |
| spectator_tokens | id, token_hash, tournament_id, created_at, expires_at, revoked_at | 관객 화면 링크. 만료 = min(생성+48시간, 대회 종료+24시간) |
| tournament_viewers | tournament_id, user_id, token_id, expires_at | 토큰을 확인받은 관객. 채널 구독 권한의 근거 |
| rate_limits | key, window_start, count | 기기·IP별 요청 제한 카운터 |

match_attempts.status 값: ready, countdown, playing, paused, judging, done. result_reason 값: solved, fewer_blocks, faster, distance, teacher, bye, forfeit.

### 읽기 권한 (RLS)

- 교사: teachers에 있고 그 행사·대회의 teacher_id인 경우에만 하위 데이터 전체를 읽는다. 변경은 API로만 한다(로그 누락 방지).
- 선수(익명 인증): 자기 대회의 matches·match_attempts와 자기 match_records·match_runs만 읽는다. 상대의 프로그램은 읽을 수 없고, 상대 정보는 공개 뷰(성공 여부, 실행 횟수, 제출 완료)로만 본다.
- 확인된 관객: tournament_viewers에 만료 전으로 등록된 동안 그 대회의 경기·프로그램을 읽는다.
- ranking_entries: 직접 조회 권한을 주지 않는다. 공개 랭킹은 서버 API가 순위·표시용 번호·닉네임·별 수·깬 단계 수만 내보낸다. RLS는 행만 가리고 컬럼은 가리지 않으므로, entry_key_hash 같은 비밀 컬럼이 있는 테이블은 공개 조회를 열지 않는다.
- stage_events, rate_limits, spectator_tokens: 클라이언트 접근 없음(서버 전용).

### 보관과 삭제

- 행사 당일 운영 교사가 행사 후 7일 안에 대시보드의 「행사 데이터 삭제」를 누른다. 이것이 기본 절차이고 책임자는 그 교사다.
- 삭제 대상: 그 행사의 랭킹·통계·대회·경기·실행·로그·관객 토큰·관객 등록·제한 카운터, 그리고 그 행사에서 만들어진 익명 사용자(auth.users). 익명 사용자는 자동으로 정리되지 않으므로 서버가 Admin API로 지운다.
- 보조 장치로 pg_cron이 매일 30일 지난 데이터를 지운다. 무료 프로젝트는 1주일 미사용 시 정지되어 cron도 멈추므로 자동 삭제만으로는 30일 이내 삭제를 보장하지 못한다.

## 12. 실시간 통신 규격

실시간 메시지는 화면 표시용이고, 승패의 근거는 서버가 검증해 DB에 저장한 기록뿐이다. 모든 채널은 Realtime Authorization을 켜 비공개 채널로 만들고, realtime.messages RLS에서 받기(SELECT)와 보내기(INSERT) 권한을 따로 준다.

### 채널과 권한

| 채널(토픽) | 보내기(INSERT) | 받기(SELECT) | 오가는 것 |
|---|---|---|---|
| tournament:{id} | 서버만 (Presence는 참가자 본인 상태만) | 그 대회 참가자·교사·확인된 관객 | 대기실 접속 상태, 대진 갱신, 라운드 시작, 결과 확정 |
| match:{id} | 서버만 | 그 경기 선수·교사·확인된 관객 | 시도 상태, 선수 상태(실행 결과·제출 완료) |
| match:{id}:watch:{playerId} | 그 선수 본인만 | 교사·확인된 관객만 (선수는 받지 못함) | 그 선수의 블록 편집·실행 프로그램 |

선수는 상대의 watch 채널을 받을 수도, 상대 명의로 보낼 수도 없다. 서버만 보내는 채널은 클라이언트가 가짜 「경기 종료」를 보낼 수 없다. 그래도 클라이언트는 상태를 바꾸는 이벤트를 받으면 match_attempts 행을 다시 읽어 확인한 뒤 화면을 바꾼다.

### 이벤트

| 이벤트 | 채널 | 보내는 쪽 | 내용 | 받아서 하는 일 |
|---|---|---|---|---|
| countdown | match | 서버(시도 시작 API) | attempt_id, layout_id, variant, theme_id, start_at, ends_at | 맵을 열고 서버 시각 기준 3-2-1 후 시작 |
| run_result | match | 서버(run API) | attempt_id, player_id, run_id, solved, blocks | 상대는 「실행 중·성공!」 표시, 관전은 기록 갱신 |
| player_done | match | 서버(done API) | attempt_id, player_id | 「제출 완료」 표시 |
| paused / resumed | match | 서버(교사 조작) | attempt_id, paused_ms, ends_at(재개 시 새 값) | 타이머 멈춤·재개, 조작 잠금 |
| attempt_ended | match | 서버(judge API) | attempt_id, winner_id 또는 rematch_pending, reason | 결과 화면 또는 「재경기 대기」 |
| program_changed | watch:{player} | 선수 | program, version (300ms 디바운스) | 관전 화면이 블록 목록 갱신 |
| run_started | watch:{player} | 선수 | run_id, program, version | 관전 화면이 1배속으로 애니메이션 재생 |

### 서버 API (모두 호출자 권한·현재 시도 id·상태를 확인)

- POST /api/tournament/attempt/start (교사, 시도가 ready): 맵을 배정하고 start_at = 현재 + 4초, ends_at = start_at + 제한시간을 저장한 뒤 countdown을 보낸다.
- POST /api/tournament/attempt/run (그 시도의 선수, 실행을 누른 즉시): attempt_id·run_id·program을 보낸다. 서버는 상태가 playing이고 접수 시각이 start_at 이상 ends_at 이하인지, 제출 완료 전인지, run_id가 처음인지(아니면 기존 결과 반환), 프로그램이 허용 블록·중첩·크기 제한을 지키는지 확인한다. 엔진으로 실행해 match_runs에 저장하고, 더 좋은 기록이면 match_records를 갱신한 뒤 run_result를 보낸다. 경과 시간 = 접수 시각 − start_at − paused_ms.
- POST /api/tournament/attempt/done (선수): 성공 기록이 있을 때만 허용하고 멱등하다.
- POST /api/tournament/attempt/pause · resume (교사): 일시정지 중에는 run을 거부한다. 재개 시 paused_ms를 더하고 ends_at을 그만큼 늦춘다.
- POST /api/tournament/attempt/judge (그 대회의 누구나): 두 선수 모두 제출 완료이거나 현재 시각이 ends_at을 지났을 때만 판정한다. 멱등하며(이미 판정된 시도는 같은 결과 반환), 둘 다 실패면 재경기 시도를 ready로 만든다.
- POST /api/tournament/match/winner · forfeit · rematch (교사): matches.locked이면 거부. 조작과 match_logs 기록을 한 트랜잭션으로 처리한다.
- GET /api/tournament/match/snapshot (선수·교사·관객): 현재 시도 상태와 기록. 선수에게는 상대 프로그램을 빼고 보낸다.
- GET /api/time: 서버 시각. 클라이언트는 접속 시 3번 측정해 시계 차이를 보정한다.

판정을 누가 부르나: ends_at이 지나도 서버 함수가 저절로 실행되지는 않는다. 그래서 세 곳에서 판정을 호출한다. ① 선수 화면은 ends_at이나 양쪽 제출 완료 시. ② 교사 운영 화면은 2초마다 마감 지난 playing 시도에 대해. ③ 대회 관련 API가 불릴 때마다 미판정 시도를 정리한다. 판정이 늦게 불려도 기록 마감은 ends_at으로 고정이다. Vercel Cron은 경기 마감용으로 쓰지 않는다.

### 시도 상태 전이

ready → countdown → playing → judging → done. 교사는 playing을 paused로 멈추고 다시 playing으로 돌릴 수 있다. 둘 다 실패하면 이 시도는 done으로 끝나고, 한 등급 쉬운 맵의 새 시도가 ready로 만들어져 교사의 시작을 기다린다.

교사가 승자를 직접 지정하면 어느 상태에서든 바로 경기가 끝난다. 부전승 경기는 시도 없이 결과만 기록한다.

### 연결 끊김과 재접속

- 선수 화면은 현재 프로그램을 localStorage에 계속 저장하고, 재접속하면 snapshot API로 시도 상태·ends_at·자기 기록을 받아 이어서 한다. 다른 시도의 프로그램은 버린다.
- Presence에서 10초 이상 사라진 선수는 교사 운영 화면에 경고로 표시한다. 타이머는 자동으로 멈추지 않는다(공정성). 교사가 일시정지·재경기·기권 중 고른다.
- Realtime 연결이 끊기면 supabase-js가 자동 재연결하고, 재연결 직후 snapshot을 다시 읽는다. 놓친 표시용 이벤트는 다시 받지 않는다.

연결 수 추정: 선수 24 + 교사 1~2 + 관객 화면 1~2 = 약 30개. 랭킹판과 개인 모드는 Realtime을 쓰지 않는다. 메시지 처리량·권한 검사·재접속·동시 판정은 24명 시뮬레이션으로 실제로 확인한다(14절).

## 13. 비기능 요구사항

행사장 Wi-Fi와 무료 요금제를 전제로 가볍고 끊김에 강하게 만든다.

### 성능과 호환성

- 첫 화면은 행사장 Wi-Fi에서 3초 안에 떠야 한다. 이미지는 SVG, 레이아웃은 정적 JSON으로 번들에 포함한다.
- 로봇 애니메이션은 저사양 태블릿에서도 끊김 없이 움직여야 한다.
- 지원 브라우저: 최신 Chrome, Safari(iOS·iPadOS), 삼성 인터넷, 전자칠판 내장 브라우저. 전자칠판은 기종마다 다르므로 행사 전 실기기로 확인한다.
- 최초 온라인 접속에서 준비를 마친 기기는 네트워크를 끈 뒤에도 개인 모드의 모든 단계 이동과 새로고침이 된다(4·10절). 처음부터 오프라인인 접속은 지원하지 않는다.

### 무료 요금제 한도

| 항목 | 무료 한도 | 예상 사용 |
|---|---|---|
| Supabase Realtime 동시 연결 | 200 | 약 30 (토너먼트만) |
| Supabase Realtime 메시지 | 월 200만 | 대회 1회에 많아야 수만 건 (추정) |
| Supabase DB 용량 | 500MB | 수 MB |
| Supabase 활성 프로젝트 | 2개 | 1개 |
| Supabase 비활성 정지 | 1주일 미사용 시 일시 정지 | 행사 전날 복원·점검 필수 |

출처: Supabase Pricing, Neon vs Supabase 무료 플랜 비교. 한도는 바뀔 수 있으므로 행사 전에 다시 확인한다.

학교 Wi-Fi와 익명 로그인 한도: Supabase 익명 로그인은 IP당 시간당 30회로 제한되고 대시보드에서 바꿀 수 있다. 학교 Wi-Fi에서는 모든 기기가 한 IP로 보여 24명 대회 한 번에 거의 다 쓰게 된다. 행사 전 Authentication > Rate Limits에서 300회 정도로 올리고, 기기에 저장된 익명 세션을 재사용해 재접속 때 다시 로그인하지 않게 한다.

메일 발송 한도: Supabase 기본 메일 발송은 프로젝트 전체에서 시간당 몇 통으로 제한되고 자체 SMTP를 연결해야만 바꿀 수 있다. 그래서 교사 로그인은 메일이 필요 없는 이메일 + 비밀번호 방식으로 한다.

신규 가입 설정: Supabase에서 신규 가입 허용을 끄면 기존 사용자만 로그인할 수 있고, 익명 로그인도 새 사용자로 취급되어 거부된다. 그래서 신규 가입은 켜 두고, 누가 이메일로 가입하더라도 teachers에 없으면 아무 권한이 없도록 RLS·API를 설계한다. Realtime Authorization(비공개 채널)도 대시보드에서 켜져 있어야 한다. 이 설정 조합은 0단계에서 실제로 확인한다.

Vercel Hobby 조건: Hobby는 비상업·개인 용도로만 쓸 수 있다. 참가비·후원 같은 금전적 이익이 없는 학교 행사라면 맞는 것으로 보이지만, 운영 기관에서 한 번 확인한다. 저장소는 개인 GitHub 계정 소유로 만드는 것이 안전하다.

### 개인정보·안전

- 학생의 실명·학교·학년·연락처는 받지 않는다. 닉네임만 저장한다.
- 행사·대회 데이터는 행사 후 교사가 삭제하고, 늦어도 30일 안에 지운다.
- 외부 광고·분석 도구를 넣지 않는다. 성공 지표는 개인정보 없는 자체 통계(stage_events)와 대회 기록으로만 잰다.
- 참가 코드 입장은 기기당 1분에 10회로 제한해 코드 추측을 막는다.
- 교사 계정은 운영자가 대시보드에서 만들고, 교사 권한은 teachers 테이블에 등록된 사용자 ID로만 준다. 앱에는 이메일 가입 화면을 만들지 않는다.

### 접근성

- 글자와 배경의 대비는 WCAG AA(4.5:1) 이상.
- 색만으로 구분하지 않는다. 애니메이션을 줄이는 설정(prefers-reduced-motion)을 따른다.

## 14. 개발 단계와 완료 기준

Claude Code는 아래 9단계를 순서대로 진행하고, 각 단계는 완료 기준을 모두 만족해야 다음으로 넘어간다. 위험이 큰 인증·채널 권한·실시간 대결을 작은 맵 세트로 먼저 검증한 뒤 콘텐츠를 늘린다. 0~7단계가 행사에 필요한 필수 범위이고, 8단계는 여유가 있을 때 추가한다.

## 15. 운영 체크리스트와 범위

무료 Supabase는 1주일 동안 쓰지 않으면 일시 정지되므로, 행사 전날 점검이 가장 중요하다.

### 행사 전

- [ ] 실제 행사 기기(휴대폰, 태블릿, 전자칠판)에서 개인 모드 1장과 4명 테스트 대회를 진행한다.
- [ ] 행사장 Wi-Fi에서 접속을 확인하고, 휴대폰 핫스팟을 백업으로 준비한다.
- [ ] 교사 대시보드에서 행사를 만들고 접속 QR을 인쇄한다.
- [ ] 운영에 참여할 교사 계정을 Supabase 대시보드에서 만들고 로그인을 확인한다. 같은 곳에서 익명 로그인 시간당 한도를 300회 정도로 올리고 신규 가입 허용(익명 로그인에 필요)과 Realtime Authorization이 켜져 있는지 확인한다.

### 행사 전날

- [ ] Supabase 대시보드에서 프로젝트가 활성 상태인지 확인하고, 정지되었다면 복원한다.
- [ ] 배포 주소에서 랭킹 등록과 2명 테스트 경기를 한 번씩 실행한다.
- [ ] 테스트로 만든 랭킹 항목과 대회를 지운다.

### 행사 당일

- [ ] 전자칠판 하나에 랭킹 화면(?screen=1)을, 다른 하나에 관객 화면을 띄운다.
- [ ] 부스 기기는 홈 화면에 두고, 학생이 바뀔 때 「다음 친구에게 넘기기」를 누른다.

### 행사 후

- [ ] 필요하면 결과를 기록해 두고, 교사 대시보드에서 행사·대회 데이터와 익명 사용자를 7일 안에 직접 삭제한다(「행사 데이터 삭제」 버튼). 프로젝트가 정지되면 자동 삭제가 돌지 않기 때문이다.

### 범위 밖 (이번에 만들지 않음)

- 학생 회원가입과 행사 간 기록 연동
- 팀 대항전, 3명 이상 동시 대결
- 교사용 맵 편집기
- AI 기능, 음성 안내, 다국어
- 유료 요금제가 필요한 기능

### 열린 질문

- 행사 이름·로고를 화면에 넣을지, 넣는다면 어디에 넣을지
- 로봇 캐릭터 이름을 붙일지
- 대회 제한시간 기본값 180초가 저학년에게 적당한지(테스트 대회에서 확인)
- 15단계를 10~20분에 끝낼 수 있는지, 1·2학년이 1장을 혼자 완주하는지(저학년 사전 테스트)
- Vercel Hobby 사용이 운영 기관 기준으로 비상업에 해당하는지

## 구현 메모 (PRD와 다르게 구현한 점과 이유)

1. **잠금 단위**: PRD 10절은 "시도 행을 잠근 Postgres 함수"를 말한다. 구현은 서버가 대회 상태 전체(대회·선수·경기·시도·기록, 24명 기준 수십 행)를 읽어 순수 TS 상태 기계(`src/tournament/machine.ts`)로 바꾼 뒤, `commit_tournament(p jsonb)` 함수 하나가 **대회 행을 `SELECT … FOR UPDATE`로 잠그고 버전을 비교한 뒤** 바뀐 행·실행·로그를 한 트랜잭션으로 저장한다(낙관적 잠금 + 재시도). 판정 규칙이 TS 엔진에 있어야 서버 재실행과 테스트가 같은 코드를 쓰기 때문이다. 결과가 하나로 정해지는 성질은 같고, 잠금 범위가 대회 단위로 넓어졌다. 24명 규모에서는 충돌 재시도로 충분하다(시뮬레이션 스크립트로 확인).
2. **match_runs.run_id 유일성**: run_id는 클라이언트가 만든 난수라 `(attempt_id, run_id)` 쌍으로 유일하게 했다.
3. **시각 컬럼**: 판정이 밀리초 단위이므로 `*_at` 컬럼은 밀리초 epoch(bigint)로 저장한다.
4. **추가 컬럼**: matches.needs_teacher(완전 동점 표시), match_attempts.kind(first·auto·extra), match_records.last_run_id·last_program·last_final(관전 snapshot의 "마지막 실행 프로그램과 로봇 최종 위치"), tournaments.start_players·champion_id·screen_match_id(관객 화면이 따라갈 경기)·finished_at·version, ranking_entries.player_session·display_no(표시용 번호).
5. **로컬 개발 백엔드**: Supabase 환경 변수가 없으면 같은 API가 프로세스 메모리 저장소 + SSE 채널로 동작한다(`src/server/store/memory.ts`, `/api/rt/*`). 채널 권한은 SQL의 `rt_can_receive`/`rt_can_send`와 같은 규칙을 `src/server/rtAuth.ts`에 구현했다. 배포(Vercel)에서는 반드시 Supabase를 쓴다.
6. **레이아웃 생성**: 44개 레이아웃은 `scripts/generate-layouts.ts`가 무작위로 만들고 전수 탐색(반복 심화)으로 가장 짧은 풀이를 찾아 target으로 쓴다. 등급마다 "바로 아래 개념으로는 목표 안에 풀리지 않음"을 확인한다(D3: 순차만으로는 목표+2 이하 불가, D4: 중첩 1로는 목표 이하 불가, D5·D6: 아래 개념으로 목표 이하 불가 + 순차만으로는 목표+4 이하 불가). 모든 레이아웃이 60초 안에 검증되어 targetVerified = true다.
7. **색 조건 팔레트**: 「만약 바닥이 색이라면」은 팔레트에 「빨강이면(▲)」「파랑이면(●)」 두 개로 둔다(프로그램 안에서 탭해 색을 바꿀 수도 있다). 색 타일은 빨강 = 빗금 + ▲, 파랑 = 점무늬 + ● 로 색 없이도 구분된다.
8. **테마 파일**: SVG 컴포넌트가 들어 있어 `content/themes.tsx`이고, React 없는 모듈용 id 목록은 `content/themeIds.ts`에 둔다.
9. **관객 화면 회수**: 회수하면 서버가 `screen_closed`를 보내고 관객 화면이 닫힌다. 이후 snapshot·state API와 재구독은 거부된다. Supabase에서 이미 열린 Realtime 연결이 즉시 끊기는지는 실제 프로젝트에서 0단계로 확인해야 한다(아래 README 참고).
10. **시각 디자인 (파스텔 미니멀 2.5D)**: 맵은 하늘에 떠 있는 석판 위에 물체가 서 있는 2.5D로 그린다. 아이소메트릭(마름모)이 아니라 **북쪽 = 화면 위**를 유지한 비스듬한 시점이다. 저학년이 「앞으로」 화살표와 로봇 방향을 헷갈리지 않게 하기 위함이다. 로봇은 바라보는 방향마다 앞·뒤·옆 모습이 바뀌고 발밑에 방향 화살표가 있다. 물체·로봇은 테두리 없는 기하학 도형에 빛·그늘 두 톤 음영이다. 블록·버튼은 파스텔 바탕에 진한 잉크색 글자(대비 4.5:1 이상, 13절)로 했다. 특정 게임의 캐릭터·건축을 베끼지 않고 분위기만 참고했다. 테마 6종의 이름·로봇·목적지·장애물은 5절 표 그대로다.
11. **개인 모드 체험판**: `scripts/build-demo.mjs`가 개인 모드만 HTML 한 장으로 묶는다(서버 없이 15단계). `window.__ROBOT_DEMO__`가 켜지면 홈 링크·랭킹 등록·서버 전송을 숨기고 끈다. 랭킹·대회는 정식 사이트에서만 된다.
12. **배포에서 메모리 백엔드 차단**: Supabase 환경 변수 없이 배포(Vercel·프로덕션)되면 랭킹·대회 API가 503 「서버 설정이 필요해요」를 돌려준다. 서버리스에서는 데이터가 사라지고 개발용 교사 계정이 열리기 때문이다. 로컬 `next start`·E2E는 `ALLOW_MEMORY_BACKEND=1`로 허용한다.
13. **배포 설정 (실제 적용값)**:
    - Vercel 함수 지역은 Supabase와 같은 서울(`icn1`, `vercel.json`). 미국 동부에 두었을 때 실제 사이트 24명 시뮬레이션에서 응답 p95가 8초였다(대회 API가 DB를 여러 번 오가므로).
    - Supabase Realtime: 「비공개 채널만(private only)」과 **Presence 켜기**가 필요하다. 새 프로젝트는 Presence가 꺼져 있을 수 있다(대기실 접속 상태·교사 화면 「접속 끊김」 경고가 Presence를 쓴다). 15절 행사 전 체크리스트에 더한다.
    - 교사 계정을 대시보드에서 만들 때 「Auto Confirm User」를 켜야 비밀번호 로그인이 된다.
    - Next.js는 보안 패치 버전(15.5.28, CVE-2025-66478)을 쓴다. Vercel은 취약한 버전의 배포를 막는다.
14. **검증 현황**: 실제 사이트(Supabase + Vercel)에서 24명 시뮬레이션 대회 완료(5라운드 23경기), 익명 로그인·교사 권한 거부·비공개 채널 거부 확인. 14절 0단계 중 「관객 토큰 회수 후 이미 열린 Realtime 연결이 끊기는지」와 저학년 사전 테스트(15단계 10~20분)는 아직 실제로 확인하지 않았다.
